# W3-02 gate: run observability and cancellation surface

- Wave: 3
- Date: 2026-10-21
- Status: **passed locally on Windows**

## Scope

The read and control surface an operator needs before the run loop lands:

- list a run's journal events (`silyn runs events`);
- list a run's tool-call ledger, including `Indeterminate` rows
  (`silyn runs tools`);
- request cancellation through the cross-process cancel file
  (`silyn runs cancel`).

`silyn run` is unchanged: it still exits 5 with
`runtime loop is not available until W3` and creates no run. The runtime loop
itself belongs to W3-01; this task only exposes and tests the contract.

## Command surface

| Command | JSON | Human |
|---|---|---|
| `silyn runs events <run-id>` | array of `EventEnvelope` | `seq<TAB>type<TAB>occurred_at<TAB>event_id` |
| `silyn runs tools <run-id>` | array of ledger records incl. `state` | `step_id<TAB>tool_name<TAB>state<TAB>call_id<TAB>result_ref` |
| `silyn runs cancel <run-id>` | `{"run_id","path","already_requested"}` | `path:` / `already_requested:` lines |

- Human event/tool output is unpadded TSV with no header, so it can be piped
  through `cut`/`awk`. `result_ref` prints `-` when absent. An existing run with
  no events or no ledger rows prints nothing and exits 0.
- Event and state names use the JSON wire names (`run_started`,
  `step_completed`, `started`, `indeterminate`, ...).
- Global `--json` works before or after the subcommand. Errors stay on stderr as
  `{"error": {"class","message"}}` and never include file content or secrets.
- Unknown run and terminal run both map to `ErrorClass::Permanent` -> exit 5,
  matching `runs show`.

## Cancel protocol (frozen)

- Path: `<home>/run/<run_id>.cancel`, where `<home>` is `SILYN_HOME`.
- `runs cancel` validates the run exists and is non-terminal, creates `run/`,
  and writes an empty file. The write uses `create_new`, so the existence check
  and the write are one atomic step: concurrent or repeated requests leave
  exactly one file and report `already_requested: true`.
- `already_requested` is `false` only for the call that created the file.
- The CLI never updates run status; the runtime (W3-01) polls the file and
  performs the `Cancelled` transition. The test asserts the run row is still
  `running` after `runs cancel`.
- A terminal run (`completed`, `failed`, `cancelled`) is a permanent error and
  no file is written. An unknown run is a permanent error and no `run/`
  directory is created.

## Storage addition

`ToolLedger::list_by_run(run_id)` returns the ledger of one run ordered by
`created_at`, then `step_id`, then `tool_call_id`. Row decoding lives in one
private `from_row` helper shared with `get`, so the two reads cannot drift.

The app layer validates the run through `RunRepository::get` before reading the
journal or the ledger, which is why an unknown id is `Permanent` rather than an
empty list.

## Notes

- Tests seed the agent/session/task/run chain and journal/ledger rows through
  `silyn-storage` (`silyn-cli` dev-dependency only), because no CLI command
  creates a run until W3-03. The seeded run ids are real UUIDv7 values, so the
  CLI paths are exercised end to end.
- `silyn-app` gained a direct `serde` dependency for the `CancelRequest` JSON
  shape, and dropped the unused `silyn-runtime` dependency. Frontends still
  import records through `silyn_app` re-exports.
- `request_cancel` uses blocking `std::fs` for one directory creation and one
  empty-file write; both are single syscalls and match the existing
  `App::open` style. No `spawn_blocking` is needed at this size.
- Cancel files are never removed by this task. Removing them after the runtime
  observes them is the runtime's responsibility (W3-01), so the file cannot
  disappear between validation and polling.

## Deferred

- `runs resume` and `silyn run`: W3-03.
- Live event streaming (`tail`/follow): the current surface is a snapshot read;
  an append-driven stream needs the runtime event sink.
- Run status transitions on cancellation (`Running -> Cancelled`, terminal
  event, `finished_at`): owned by the runtime loop, not the CLI.
- Cancelling a task or all runs of a task: out of scope; the signal is per run.
- Retention of cancel files and of the `run/` directory: deferred until the
  runtime consumes signals.
