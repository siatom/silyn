- Wave: 7

- Crate: [`silyn-api`](../../crates/silyn-api/src/lib.rs)

## Scope

Add a thin local HTTP surface over `silyn-app` for the W7 productization gate.
The crate is a transport adapter, not a second service layer:

- `lib.rs` exposes `router(ApiState) -> axum::Router`, `serve(app, addr, token)`,
  `serve_with(...)`, `ApiConfig` and `ApiState`.
- Every business rule stays in `silyn-app`: validation, run wiring, memory
  scoping, the cancel file and the evolution gates. No SQL, no duplicated
  decision logic and no new DTOs for app records.
- Single-tenant, loopback-only by default, no CORS layer, no TLS. Cron jobs,
  proxies and remote clients are out of scope; the token is a shared secret, not
  an authorization system.

One small app helper was added (`silyn-app::default_model`, in
`crates/silyn-app/src/api_support.rs`) so the HTTP run body and the CLI resolve
`SILYN_LLM_MODEL` through the same rule.

## Routes

`/health` is public; every `/v1/*` route is behind the optional token.

| Method | Path | Body | Success | Behavior |
|---|---|---|---|---|
| GET | `/health` | – | `200` | `{status:"ok", version}`; no database access, no paths |
| POST | `/v1/agents` | `{owner_id}` | `201` | creates an agent |
| GET | `/v1/agents` | – | `200` | agents, newest first |
| POST | `/v1/agents/{id}/sessions` | – | `201` | creates a session for an existing agent |
| GET | `/v1/agents/{id}/memories?q=&limit=` | – | `200` | agent-scoped FTS search; `limit` defaults to 8 and is capped at 200 |
| POST | `/v1/tasks` | `{session_id, objective, budget?}` | `201` | records an objective in `created` |
| POST | `/v1/tasks/{id}/run` | run options | `200` | creates and executes a run, returns `RunOutcome` |
| POST | `/v1/runs/{id}/resume` | run options | `200` | resumes a non-terminal run |
| GET | `/v1/runs/{id}` | – | `200` | `RunRecord` |
| GET | `/v1/runs/{id}/events` | – | `200` | SSE: replay then poll until terminal |
| POST | `/v1/runs/{id}/cancel` | – | `200` | writes the cancel file, returns `{run_id, path, already_requested}` |
| GET | `/v1/evolution/candidates?agent_id=` | – | `200` | candidates of one agent |
| GET | `/v1/evolution/candidates/{id}?agent_id=` | – | `200` | candidate plus evaluations, promotions, audit |
| POST | `/v1/evolution/candidates` | `{agent_id, patch}` | `201` | runs static checks and stores `static_checked` |
| POST | `/v1/evolution/candidates/{id}/evaluate` | `{agent_id, report, stats}` | `200` | attaches a sealed evaluation projection |
| POST | `/v1/evolution/candidates/{id}/promote` | `{agent_id}` | `200` | promotion gate; `decision` may be `reject` |
| POST | `/v1/evolution/promotions/{id}/rollback` | `{agent_id}` | `200` | restores the previous policy version |

The two `GET /v1/evolution/candidates` routes are additive: the task package
lists the evolution writes, and an operator (and the gate tests) needs to list
and show what was submitted.

Run options on `/run` and `/resume` use the CLI flag names, all optional:
`offline`, `model`, `capabilities` and `budget`
(`max_steps`, `max_input_tokens`, `max_output_tokens`, `max_cost_usd`,
`max_wall_secs`). An empty body means "all defaults". `offline: true` selects the
deterministic mock provider, so the surface can be exercised without a key or a
network. A failed or cancelled run is a `200` with the status in `RunOutcome`,
matching the CLI, whose exit code carries the same information.

## Authentication

- `SILYN_API_TOKEN` (trimmed, blank means "no authentication") enables bearer
  auth for every `/v1/*` route; `/health` stays public.
- Accepted header: `Authorization: Bearer <token>` (case-insensitive scheme).
- The comparison hashes both values with SHA-256 and compares the 32-byte
  digests without early exit, so neither a prefix nor a length difference leaks
  through timing.
- Missing or wrong tokens return `401` with `WWW-Authenticate: Bearer` and the
  generic message `missing or invalid bearer token`; the presented or expected
  token is never echoed.
- With no token configured the loopback boundary is the only protection. That is
  deliberate for a single-user local tool and is stated in
  [security](../security.md).

## Bind policy

- `SILYN_API_ADDR` (default `127.0.0.1:7788`); a malformed address is a permanent
  error rather than a silent fallback.
- `SILYN_API_ALLOW_NON_LOOPBACK=1` (also `true`/`yes`) is required to bind a
  non-loopback address. The check runs before `TcpListener::bind`, so a
  misconfigured server never listens on a routable interface, even briefly.
- Ctrl-C triggers graceful shutdown; in-flight requests finish and the port is
  released.

## SSE contract

`GET /v1/runs/{id}/events` is `text/event-stream`:

```text
id: 4
event: run_completed
data: {"event_id":"...","aggregate_id":"...","seq":4,"schema_version":1,"occurred_at":"...","correlation_id":null,"event":{"type":"run_completed"}}
```

- `id:` is the journal sequence, `event:` the `RunEvent` serde tag
  (`run_created`, `run_started`, `step_completed`, `tool_failed`, `run_verified`,
  `run_completed`, `run_failed`, `run_cancelled`) and `data:` the full
  `EventEnvelope`.
- The stream replays existing events, then re-reads the journal every 250 ms and
  forwards events with a higher sequence until the run is terminal or the client
  disconnects.
- Status is read **before** the events in each iteration, so a terminal status is
  only observed after every event committed with it has been sent. This closes
  the race where a run completes between the replay and the first poll.
- An unknown run is a `404` before the response starts; the stream is never
  opened just to close immediately.

## Error mapping

Bodies are `{"error":{"class","status","message"}}`. `class` matches the CLI's
`--json` taxonomy exactly; `status` is the HTTP mapping. Messages are the bounded
`SilynError` display strings: no stack traces, no request bodies, no headers and
no API keys.

| Service error | Status | Class |
|---|---|---|
| `Permanent` containing `not found` | `404` | `permanent` |
| `Permanent` (validation, state conflict) | `400` | `permanent` |
| `Schema` (bad body, bad evaluation document) | `400` | `permanent` |
| `PolicyDenied`, `InvalidTransition` | `403` | `policy_denied` |
| `Indeterminate` | `409` | `indeterminate` |
| `Transient` | `503` | `transient` |
| `Storage`, `Model` | `500` | `permanent` |
| Missing/wrong bearer token | `401` | `unauthenticated` |

Path parameters are parsed by hand and bodies with `serde_json`, so a malformed
id or JSON body produces the same JSON error shape instead of a plain-text axum
rejection.

## Evaluation attachments

`silyn-app::attach_evaluation` reads two files from disk. The route writes the
`report` and `stats` JSON bodies under `<home>/tmp/evaluation/` using exclusive
creation (`create_new`) with UUID names and mode `0600` on Unix, then calls the
service, which performs the full cross-check (schema version, candidate id,
suite version, verdict agreement, finite gains, declared evidence runs). The
files are kept after a successful attachment so `evaluation_runs.report_path`
stays resolvable, and removed when the service rejects the documents. No
database row is written before validation passes.

## Known gaps

- **SSE replay is not cursor-based.** Every 250 ms poll re-reads the whole journal
  of the run and de-duplicates by sequence. That is correct and simple, but the
  per-poll cost grows with journal size; a large run should query by
  `seq > last_seq` when the journal exposes that filter. No keep-alive comments
  are emitted, so a proxy with a short idle timeout could close a long stream.
  Loopback-only usage makes that acceptable for this gate.
- **Evaluation files have no retention policy.** They are private UUID-named
  files under `<home>/tmp/evaluation/` and are kept on success for audit. There
  is no purge command; deleting them manually breaks the recorded `report_path`
  (the sealed checksum and metrics in `metrics_json` remain authoritative).
- **`budget` on task creation is validated but not persisted.** `tasks` has no
  budget column and migrations are out of this task's scope, so the enforced
  budget is the one sent to `/v1/tasks/{id}/run`. A client that relies on a
  creation-time cap is not protected by it.
- **No external sandbox and no multi-tenant isolation.** The surface is local and
  single-tenant: one shared token, no per-user authorization, no TLS, no audit of
  HTTP callers. As with the CLI, anything that can reach the loopback port and
  the token can act as the operator.
- **Token rotation needs a restart.** `SILYN_API_TOKEN` is read once at startup.
- **No API binary or `silyn serve` command.** `silyn_api::serve` is the entry
  point for the desktop shell (W7-02) and a future CLI subcommand;
  `crates/silyn-cli` was out of scope here.
- **`verify-arch` does not check `silyn-api`.** The gate keeps an explicit
  allowed-dependency map and the new crate is not in it (xtask is outside this
  task's ownership). Its direction (`silyn-api -> silyn-app`, `silyn-core`) is
  enforced by review until the map is extended.
- **Terminal-run resume is `400`, not `409`.** The app reports it as a permanent
  error; only `Indeterminate` maps to `409` per the contract.
