# W5-02 gate: immutable policy versions, candidate pipeline and audited promotion

- Wave: 5
- Date: 2026-10-21
- Status: **passed locally**

## Scope

The L2 evolution control plane: immutable `policy_versions`, the restricted
`PolicyPatch` protocol with static checks, the candidate state machine, the
evaluation-report promotion gate (low-risk auto, default deny) and audited
rollback. Migration `0005_evolution.sql` adds `policy_versions` (with `BEFORE
UPDATE`/`BEFORE DELETE` triggers), `evolution_candidates`, `evaluation_runs`,
`metric_samples` and `promotions`.

Non-goals: running evaluations (W5-01), CLI commands (W5-03/W7), L3 code or tool
changes, sealed-suite access.

## Contracts

- `PolicyArtifact` — `schema_version`, `context { memory_budget_ratio,
  retrieval { bm25_k, max_evidence } }`, `planner { prompt_fragments, rules,
  stop_conditions }`, `tools { allowlist }`, `verification { checkers }`.
  The nested struct is `PolicyVerification`, kept distinct from the verifier's
  `VerificationPolicy` (which decides how checker results combine).
- `PolicyVersionRecord` / `PolicyStore` — `create`, `get`, `latest`, plus the
  additive `active` (the version `agents.active_policy_version` points at).
- `PolicyPatch` / `RiskClass` / `PatchOp` / `PatchOperation` / `ExpectedGain` /
  `CandidateRecord` / `CandidateStore` — `submit`, `get`, `transition`, `list`.
  `validate_patch` and `apply_patch` are exported so W5-03 can dry-run a patch
  without touching storage.
- `PromotionReport` / `PromotionRecord` / `PromotionStore` — `decide`, `promote`,
  `rollback`, plus `record_rollback_drill`, `get`, `list` and
  `with_policy` (threshold override for experiments).
- Reused frozen types: `CandidateState`/`LifecycleState` (core),
  `PromotionDecision` and `PromotionPolicy` (core contracts),
  `AgentRepository`/`RunRepository`/`Journal` (storage).

`silyn-core`, `silyn-storage`, `silyn-runtime`, `silyn-app`, `silyn-cli`,
`eval/suites/**`, root `Cargo.toml` and migrations `0001`–`0004` were not
touched. No new dependency was needed (`sha2`, `serde_json` and `sqlx` were
already declared by `silyn-growth`).

## Rules implemented

**Policy versions.** Content addressed: the canonical form sorts every object
key recursively and serializes without whitespace, so the same artifact built
twice has the same sha256 (`canonical_checksum_is_stable`). `create` validates
bounds (`memory_budget_ratio` 0–0.6, `bm25_k` 1–200, `max_evidence` 1–50,
non-empty unique tool allowlist and checker list, non-empty text ≤ 4000 bytes,
≤ 100 list entries). Identical content for the same agent is idempotent and
returns the existing row; identical content for another agent is a permanent
error because `policy_versions.checksum` is globally unique (prescribed DDL).
Reads recompute the checksum and refuse a row whose content no longer matches.
`BEFORE UPDATE`/`BEFORE DELETE` triggers abort any mutation
(`version_is_immutable`).

**Static checks (no evaluation run, nothing written).** `schema_version == 1`;
hypothesis non-empty, ≤ 2000 characters, no control characters; 1–20 operations;
1–50 unique evidence runs; every path must match
`^/(planner/(prompt_fragments|rules)|context/retrieval)(/.*)?$` *and* contain no
`..`/`.` segment or empty segment, so `/planner/rules/../tools` is refused
(`path_whitelist_rejects_tools`). `add`/`replace` require a value, `remove` must
not carry one and cannot delete a required field. Text values are capped at 4000
bytes, reject control characters, and reject escalation phrases matched on word
boundaries (`capability`, `tool`, `approval`, `threshold`, `oracle`, `budget`) or
substrings (`fs.`, `system prompt`). Retrieval bounds are checked at the leaf
(`/context/retrieval/bm25_k`, `/context/retrieval/max_evidence`) and at the
object form; `memory_budget_ratio` is not patchable under this schema
(`bounds_rejected`). Every evidence run must exist, be terminal
(`Completed`/`Failed`/`Cancelled`), belong to the agent's session/task chain and
carry at least one step or `run_verified` event (`evidence_must_exist`). The base
version must exist for the agent and be the active one. A submitted candidate is
written as `Proposed` and moves to `StaticChecked` inside the same transaction;
`transition` uses `CandidateState::can_transition_to`, repeats are no-ops and
illegal edges are `InvalidTransition` (`state_machine_enforced`).

**Promotion gate.** Hard failures reject: report checksum mismatch, unknown
verdict, non-finite or missing numbers, empty suite version, evidence that is
missing/non-terminal/foreign/undeclared/no longer usable, a stored patch that no
longer passes static checks, a base version that is missing or not active, a
patch that cannot produce a valid artifact or produces an identical one, and a
report that arrives before the candidate is `Evaluated`.
Auto promotion additionally requires: `risk_class = low`, every operation inside
the whitelist, `verdict = promote`, `gain_pp >= min_gain_pp` (pre-registered
`10.0` pp for `csv-stats-v1`), `ci_low_pp > 0`, `unauthorized_actions == 0`, all
evidence verified, and a successful rollback drill recorded against the same base
version and checksum. Anything else is `AwaitingApproval` — including a valid
`reject` verdict, which ADR 0008 sends to the operator path rather than rejecting
outright. With no operator the candidate stays there (`default_is_deny`).

**Promotion.** Requires an `Approved` candidate, a still-active base version and a
stored evaluation. In one transaction it creates the immutable patched version
(`parent_version = base`), switches `agents.active_policy_version`, writes the
`promotions` row and appends a `promotion.promote` audit row with the candidate,
from/to versions and checksum. A promoted artifact can never touch tools,
verification, budgets or thresholds because the patch cannot address them.
`decide` records the evaluation in `evaluation_runs`, keyed by the report
checksum so re-deciding the same report is a no-op.

**Rollback.** Restores the previous version pointer, sets
`promotions.rolled_back_at`, moves the candidate `Promoted -> RolledBack` and
appends a `promotion.rollback` audit row, all in one transaction. Rolling back a
promotion that is no longer active, or rolling back twice, is permanent.

**Rollback drill (documented choice).** The drill is an explicit audited event,
not a boolean column: `PromotionStore::record_rollback_drill(agent_id,
candidate_id, actor)` appends a `promotion.rollback_drill` audit row with
decision `pass` and details `{base_policy_version, checksum}`. The gate only
counts a drill whose base version **and** checksum match the candidate's base,
so a drill from an older policy never satisfies the condition, and no drill is
ever assumed (`drill_from_another_base_does_not_count`, `default_is_deny`).
The drill method requires a pre-promotion candidate and a non-empty actor.

## Known gaps

- **Global checksum uniqueness.** The prescribed DDL makes
  `policy_versions.checksum` globally unique, so two agents cannot share an
  identical policy version; the second `create` fails permanently instead of
  storing a second row. A per-agent unique index would need a schema change
  owned by the Architect.
- **`metric_samples` is never written.** `PromotionReport` carries no per-task
  or per-arm outcomes, so the table exists for W5-01/W5-03 to fill from the full
  report. `evaluation_runs.baseline_id` is filled with the candidate's base
  policy version because the report projection has no baseline arm id.
- **Cost and regression thresholds are not evaluated.**
  `PromotionPolicy.max_cost_ratio` / `max_regression_pp` are carried for contract
  fidelity, but `PromotionReport` has no cost or regression figures; W5-01 owns
  those numbers. `min_gain_pp` defaults to the pre-registered `10.0` pp and can
  be overridden with `PromotionStore::with_policy`.
- **No timeout for `AwaitingApproval`.** ADR 0008 says a pending candidate
  eventually becomes `Rejected`; the transition exists in the state machine, but
  no scheduler drives it. The operator approval path is W5-03.
- **`transition` carries no agent principal.** The frozen signature takes only a
  `CandidateId`, so `get` filters by agent but `transition` relies on the caller
  holding the id.
- **Agent deletion is blocked once a policy exists.** The immutable
  `policy_versions` delete trigger also aborts the `ON DELETE CASCADE` from
  `agents`, which is intentional (audit history wins) but means agents with
  history cannot be removed.
- **Prompt text is not semantically analysed.** Escalation detection is a
  word/substring list; a sufficiently creative prompt can still attempt a
  capability grab. The structural guard (paths, bounds, tools) is what makes
  that harmless.
- **No JSON schema for the new records.** `schemas/` still only holds the
  artifact and patch schemas; adding `PolicyVersionRecord`/`PromotionRecord`
  schemas is Architect-owned.
- **Deferred to later work:** evaluation execution (W5-01), CLI/HTTP surfaces
  (W5-03/W7) and canary traffic splitting (`Canary` is reachable in the state
  machine but nothing uses it yet).
