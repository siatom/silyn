# W3-01 gate: bounded resumable runtime loop

## Scope

- New `silyn-runtime` modules: `budget`, `control`, `detect`, `retry`, `run`,
  `state`; the existing `tools` broker is unchanged.
- `Runtime::run_task` / `execute` / `resume` share one recovery path driven by
  the newest validated checkpoint.
- Tool side effects go through the injected `ToolExecutor` and the
  `tool_call_ledger` state machine. A pending action is checkpointed before
  `begin(Started)`, and `Started`/`Indeterminate` rows are never replayed.
- Budgets cover steps, input/output tokens, optional cost (requires a price),
  wall clock and per-step timeout.
- Cancellation supports an in-process `RunControl` flag and an optional
  `<home>/run/<run_id>.cancel` file polled while the run is active.
- Minimal storage additions: `RunRepository::update_usage` and
  `Journal::append_run_transition` (run row + optional task row + event in one
  transaction). No migrations were added or changed.

## Coverage

`eval/acceptance/w3-01.toml` maps the ten required gate ids to tests:

- step, input-token, cost and wall-clock exhaustion produce `Failed`
- pre-set and mid-call cancel files produce `Cancelled` + `RunCancelled`
- crash during a tool call resumes to `Failed` without repeating the side effect
- a seeded `Started` ledger row becomes `Indeterminate` and blocks replay
- three identical tool fingerprints in the window fail the run
- retry retries `Transient` and stops on `Permanent`/`PolicyDenied`
- malformed model output gets exactly one repair turn
- corrupted checkpoint checksums and unknown schema versions fail loudly
- terminal runs contain `RunCreated`, `RunStarted`, `RunVerified` and
  `RunCompleted`, with matching run/task rows

Extra tests cover reuse of a ledger `Succeeded` result on resume, read-only
vs. write tool retry classification, and in-process cancellation wakeups.

## Deferred work

- True process-kill injection: the crash test aborts the Tokio task at the tool
  call. A real killed process would need an external harness around the binary.
- Persistent audit sink: broker audit events stay in `MemoryAuditSink`; wiring
  them to `audit_events` belongs to a later observability task.
- `spawn_blocking`: filesystem tools still run inline on the async executor;
  the broker is fast enough for the MVP, but large reads/profile work should
  move to a blocking pool.
- Memory retrieval, context compression and experience extraction remain out of
  scope; the runtime only consumes the injected `OutcomeVerifier`.
