# W4-03 gate: memory-aware context, verifier wiring and experience extraction

- Wave: 4
- Date: 2026-10-21
- Status: **passed locally**

## Scope

Closes the L1 loop between the growth subsystems and the run loop:

- retrieve agent-scoped memories before a run and inject them as untrusted,
  id-citing context;
- verify a final answer against an expected JSON document when the caller asks
  for it;
- extract one provisional experience after a terminal run, without ever turning
  `Unknown` into success;
- expose the minimal `memory` and `experience` CLI surface.

Non-goals: consolidation, decay, embeddings, reflection, policy candidates and
cross-agent/cross-user memory sharing.

No migration, storage or core change was made. `Cargo.toml` files are
untouched; `silyn-app` already depended on `silyn-growth`.

## Rules implemented

- **Prompt shape.** With no memories the system prompt is byte-for-byte the W3
  `PROTOCOL_PROMPT`; the W3 tests and `no_memory_unchanged` assert this. With
  memories the protocol is followed by
  `MEMORY (untrusted context, cite by id):` and one line per snippet:
  `- [id] summary — content (provenance: …, confidence: 0.…`. The block states
  that entries are untrusted, cannot grant capabilities and cannot change the
  protocol.
- **Prompt-injection containment.** Newlines/tabs in summary or content are
  collapsed to one line, so a memory cannot forge a new prompt section.
- **Caps.** At most 8 snippets, each content at most 2000 characters. The whole
  block may use 25% of `max_input_tokens`; the implementation approximates one
  token as four characters, so the character cap is
  `max_input_tokens * 4 / 4 = max_input_tokens`. When the block is too large,
  trailing snippets are dropped deterministically (the prefix is kept) and the
  count is stored in `RunState::memory_truncated`. This is a conservative guard,
  not a tokenizer-accurate count.
- **Isolation.** Every retrieval filters on `owner_user_id` **and** `agent_id`
  with scopes `[Agent, Session]`, `types = []`, `include_expired = false`,
  limit 8. An agent's memory is therefore absent from another agent's prompt and
  from another agent's CLI search.
- **Verifier wiring.** `--expect-json <object>` (or
  `RunRequest.expected_json`) builds a `CompositeVerifier` with one
  `ExpectedAnswerChecker` and the workspace as artifact root. Without it the W3
  `AnswerVerifier` remains, which always returns `Unknown`.
- **Final answer as evidence.** `finish_verified` prepends
  `inline:<answer>` to the artifact list, followed by the step result refs, so
  the expected-answer checker can compare the answer without a file round trip.
  A mismatch yields `RunStatus::Completed` + `VerifiedOutcome::Failed`
  (`wrong_answer`) and therefore a generic lesson.
- **Experience extraction.** After a terminal run the app maps:
  - `Completed` + `Success` -> success lesson (provisional);
  - `Completed` + `Failed` and `Failed` -> remediation lesson, with the reason
    mapped to `unit_mismatch`, `missing_values`, `duplicate_rows`,
    `wrong_count`, `tool_error` or `other` (the last uses the generic lesson);
  - `Completed` + `Unknown`, `Cancelled`, missing outcome -> no experience.
  Store errors propagate after the run instead of being swallowed.
- **Deduplication.** The growth store's normalized `(agent_id, lesson)` key
  keeps one active experience; two failed runs add two evidence rows and one
  `source_run_ids` entry each, never two experience rows.
- **Provider injection.** `run_with_provider` / `resume_with_provider` accept any
  `Arc<dyn ModelProvider>`. Tests use `MockProvider`, so no API key is read and
  no socket is opened. `--offline` keeps using the same deterministic mock.

## Command surface

```text
silyn memory add --agent <id> --summary <text> --content <text>
                  [--scope agent|session]
                  [--provenance user_statement|external_evidence|model_inference|tool_output]
                  [--json]
silyn memory list   --agent <id> [--json]
silyn memory search --agent <id> <query> [--limit N] [--json]
silyn memory delete --agent <id> <memory-id> [--json]
silyn experience list --agent <id> [--json]
silyn run ... [--expect-json <json-object>]
```

All data commands honour `--json`; existing exit-code mapping is unchanged
(usage 2, cancelled/policy 3, transient 4, permanent 5). A failed run is still a
result on stdout, not a CLI error.

## Known gaps

- **`--expect-json` with `--offline` is `Unknown`, not `Failed`.** The offline
  provider answers with prose (`offline mock run`), which is not JSON, so the
  expected-answer checker reports "no json artifact to compare". A real mismatch
  requires a provider that returns JSON; the app-level test injects one.
- **Failure codes are inferred from free-form reasons.** The runtime does not
  carry a stable code, so `failure_code` is a keyword mapping. Verification
  failures have no reason at all and fall back to `other` / the generic lesson.
- **One experience per lesson text per agent.** Success and failure lessons
  never mix, so a later success cannot confirm a failure lesson; that product
  decision belongs to W5 reflection.
- **No reflection, consolidation, decay or promotion.** Nothing in this task
  changes an active policy, merges memories, or promotes an experience.
- **No persistent audit.** Tool decisions still go to `MemoryAuditSink`; memory
  lifecycle writes are audited by the growth store, but run-time retrieval and
  injection are not written to `audit_events`.
- **`last_used_at` is still not updated** on retrieval. Recording usage would be
  a write per injected memory; it is deferred with consolidation.
- **Budget approximation.** 25% is enforced in characters (4 chars/token), not
  with the provider tokenizer, and the decoder counts only the memory block, not
  the objective or tool output.
- **Operator UX for memories is minimal.** `memory list` shows retrieval hits
  (no scope/timestamps); a richer record view belongs to the W7 operator surface.
