## Design notes

- **Isolation.** `get`, `search` and `relations_for` all require both the owner
  and the agent; the scope filter never widens them. `shared` scope exists in
  the schema but is only reachable when the caller lists it explicitly, and it
  still has to match the owner and agent. `put` also rejects an agent that does
  not belong to the given owner (`PolicyDenied`).
- **Relations have no principal argument.** `relate`/`supersede` therefore
  refuse to touch two memories unless they share one owner/agent pair; that is
  the only guard available without changing the frozen public signatures.
- **FTS5 quoting.** User text is split on whitespace, tokens without letters or
  digits are dropped, and each remaining token is wrapped in double quotes with
  embedded quotes doubled. Operators (`AND`, `OR`, `NOT`, `-`, `*`, `(`, `)`)
  are then literal terms, so a hostile query cannot raise a `MATCH` syntax
  error. Terms are implicitly ANDed; there is no prefix or OR support yet.
  Score is returned as `-bm25`, so higher is more relevant, and ordering is
  `bm25 ASC, importance DESC, created_at DESC`.
- **Empty query.** A query with no usable token lists the newest active
  memories (`created_at DESC, importance DESC`) instead of scanning with a
  degenerate `MATCH`. Limit is clamped to `1..=200`.
- **Validity comparison.** Timestamps are bound through SQLx in one fixed UTC
  text format, so the window check is a plain string comparison against a
  single `now` value; no per-row Rust filtering is needed and `LIMIT` stays
  meaningful.
- **Purge ordering.** Sources and relations are counted and deleted explicitly
  before the memory row (the foreign keys would cascade anyway), the FTS row is
  deleted explicitly because the virtual table has no foreign key, the blob is
  deleted only when `COUNT(*) FROM memories WHERE content_ref = ?` is zero, and
  the audit row is written in the same transaction.
- **Soft delete.** `status = deleted` hides the row from `get`/`search` but
  keeps the blob and the FTS row for audit until purge. It is audited
  (`memory.soft_delete`) because ADR 0005 requires deletions to name an actor.
- **Deduplication.** `content_blobs.id` is the sha256 hex digest, so
  `put` is idempotent by construction; `ContentStore::ref_count` counts
  memories in any status, which is exactly what purge needs.
- **Transactions.** `put`, `relate`, `supersede`, `soft_delete` and `purge`
  each run in one transaction; `expire`/`touch` are single statements.
- **Trust.** Provenance is stored verbatim and never reinterprets trust:
  `model_inference` ranks no higher than `tool_output`. `sensitivity` is
  validated against `public | private | secret`.

## Cross-crate follow-up (not fixed here)

`crates/silyn-storage/tests/storage.rs::migrations_apply_once` still asserts
`COUNT(*) FROM _sqlx_migrations == 2`. Any new append-only migration makes that
hard-coded count stale, so `cargo test --workspace` now fails on that one test
even though `cargo test -p silyn-growth` is green. `crates/silyn-storage/**` is
outside this task's write scope.

Suggested fix for the integrator:

```rust
// after storage.migrate()
assert!(count >= 2, "W0 migrations must be applied");
// and keep the existing idempotency assertion:
assert_eq!(count_after, count);
```

or derive the expectation from `migrations/checksums.txt` instead of a literal.

## Deferred

- **Embeddings / vector search.** `embedding_version` is reserved and always
  `NULL`; retrieval is lexical FTS5 only, as specified for W4.
- **Consolidation and reflection.** Extracting memories from runs, merging
  duplicates and reflecting on outcomes is W4-02. Nothing here calls a model.
- **Context injection.** Selecting memories into a prompt is W4-03; this task
  exposes retrieval only. `silyn_core::contracts::MemoryRepository` is not
  implemented yet because its `search` signature has no owner/agent principal,
  and adding one is an Architect contract change.
- **Retention policy.** No TTL sweeper, size cap or per-scope retention quota.
  `expire` and `purge` are caller-driven; a scheduled retention job needs a
  policy decision (and an ADR) before it can delete data on its own.
- **Sensitivity enforcement.** `secret` memories are stored and retrievable
  like any other row; redaction before logging or prompt injection belongs to
  W4-03 and the observability layer.
- **Cross-scope promotion** (session → agent → user) is not implemented; the
  scope is whatever the writer supplied.
